# 文档维护规范

> 文档类型：项目规范。生效日期：2026-11-28。

## 1. 文档目标

文档必须帮助使用者完成任务、帮助维护者理解实现，或保存可追溯的研究证据。避免复制代码后长期失去同步，也不要把研究候选误写成已上线功能。

## 2. 推荐归属

| 内容 | 归属 |
|---|---|
| 产品定位、普通用户流程 | `docs/product/` |
| 管理员操作 | `docs/product/` |
| UI 主题与组件规范 | `docs/design/` |
| HTTP 路由、请求响应契约 | `docs/api/` |
| 部署、验收、故障排查、回滚 | `docs/operations/` |
| 来源政策、文档治理 | `docs/governance/` |
| Provider 协议与字段映射 | `docs/providers/` |
| 历史状态快照 | `docs/archive/` |

现有根目录中的历史文档暂时保留原路径，避免未审查的链接断裂；新增文档按上表归档。迁移旧文档前，必须检查相对链接、README 引用、代码注释和外部链接。

## 3. 文档头部元数据

规范和操作手册应在开头注明：
- 文档类型；
- 适用版本或适用范围；
- 最近复核日期。

状态快照必须注明：
- 记录日期；
- 对应分支、commit 或部署环境（若适用）；
- 已知限制；
- 需要重新验证的项目。

不要把「目前」「已部署」「已启用」等时态描述写成永久事实。

## 4. 事实来源优先级

1. 当前代码与自动化测试：实现行为和 API 契约。
2. 当前部署配置与 Cloudflare/GitHub 实际状态：部署状态和环境资源。
3. 规范文档：项目约束和预期行为。
4. 研究记录：候选来源证据和某次审查结论。

当代码与文档冲突时，先确认代码是否为有意变更，再更新文档；不能为了让文档看起来一致而假设实现行为。

## 5. 更新要求

- 新增/修改 API 路由时同步更新 API 参考和测试。
- 新增/修改页面流程时同步更新用户或管理员手册。
- 修改全局组件、主题变量或布局规则时同步更新设计规范。
- 修改部署工作流、环境变量或资源拓扑时同步更新运维手册和 Cloudflare 部署指南。
- 修改 Provider 协议、字段映射、限流或启用边界时同步更新对应 Provider 专项文档。
- 修改数据源目录治理规则时同步更新目录政策。

## 6. 链接与语言

- 面向用户和管理员的操作文档以中文为主，保留代码标识、协议字段和官方产品名称。
- 链接使用仓库内相对路径；变更路径时检查所有引用。
- 命令必须注明执行目录和目标环境；破坏性或部署命令应显著说明影响。
- 不得在文档中写入真实 token、API key、账号密码或私密环境 ID。

## 7. 研究记录和候选来源

候选来源即使当前不可抓取、被访问控制拦截或尚未确认协议，也应按既定治理政策保留其研究记录。明确区分：
- 研究线索；
- 已核验官方接口；
- 已实现 Provider；
- 已部署代码；
- 已登记 KV；
- 已启用来源；
- 已通过 Cloudflare hosted verification。

这些状态互不等价，不得混为一个「已支持」标签。
